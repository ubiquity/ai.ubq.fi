# Local coroutine lifetime ownership audit

The known policy-queue defect and two additional reference-capturing usage helpers in `src/admin/kernel.cpp` are repaired with captureless functions and shared result/dependency owners passed by value. The original two policy-queue `rt::all` awaits still reject fail-fast without cancelling siblings; read start order, getter error behavior, result order and callback positions are unchanged. The extra usage sites caught ordinary KV exceptions upstream, so the original rejection scenario was not asserted for them; ownership was strengthened because their closure/maps were still borrowed across suspension and post-await work had no no-throw guarantee.

No pre-fix witness, unpatched crash test, autonomous crash discovery, fuzz campaign or local clang-tidy campaign was executed. The external report, `.clang-tidy`, `tools/tidy.sh` and analysis baseline remain pool-owned.

## Coverage and limits

A bounded lexical inventory covered every regular file under `src/`, `include/`, `runtime/` and `entrypoints/`: 745 files, 150 explicitly typed lambdas and 25 remaining capturing coroutines, with zero source changes during the scan. Comments/string literals were masked; balanced captures, parameters and bodies were checked; coroutine tokens inside nested lambdas were excluded from their parent. Supplemental searches checked omitted-parameter lambda syntax and coroutine macros; only test-support rejection macros introduced coroutine tokens outside this lexical form. Every listed site was manually traced to its actual callable holder/callee. Other C++ production helper roots outside these four were enumerated; only runtime/entrypoint files were found (test, bench, fuzz and analysis code are separate).

This is a source-bound inventory of the requested closure/frame lifetime class. It is not a clean full clang-tidy baseline, a sanitizer result or a proof of all pointer lifetimes. Caller-supplied opaque callbacks retain their API contracts; the table records the reached production ownership path rather than assuming every value capture is safe. The raw `PreflightedResponsesStream::cancel` case was traced separately instead of misclassifying it as a generic owning callback.

Task evidence: `/tmp/claude-1002/prod/portability_docs/coroutine-v23/static-inventory.json` and `ownership-verdicts.json` bind every file/site hash and the verdict details. The earlier 737-file/27-site snapshot is retained as `static-inventory-before-v24.json`. All four removed admin sites are historical entries; their former line numbers are not current source locations.

## Reached holder proofs

- A: The std::function callback is a by-value parameter of the awaited handler/lock/retry coroutine, which awaits that exact callback task before releasing the parameter.
- B: rt::async copies the callable into a shared holder; callHeld owns that holder by value until the inner Task completes (rt/async.hpp:471-487).
- C: AsyncGenerator moves its Body into runGenerator by value; runGenerator awaits the body while retaining it (rt/async.hpp:1041-1059,1091-1097).
- D: SourceAlgorithm::runAsync retains shared_ptr<const function> by value, including while stream algorithms are cleared after cancellation (rt/stream.hpp:38-75,128-146,244-258).
- E: withFinally owns the cleanup callable by value and awaits its returned Task before leaving (rt/async.hpp:914-931).
- F: The cancel std::function belongs to StreamState::source; StreamState::cancel awaits it. The outer SourceAlgorithm holder owns the state-capturing forwarder until the member Task completes (chat/completions.cpp:280-285,363-374; rt/stream.hpp:38-75).

## Same-binary startup and helper roots

`runtime/startup.cpp`, its headers and all three entrypoints were included. They add no capturing coroutine lambda. `FixtureTransport::send` contains no `co_await`/`co_return`: it maps a value-owned Request and forwards a Task to its retained original transport. `FixtureRouting` owns/restores the installed transport, Codex origin and live bases while the by-value `startup::run` coroutine remains suspended on serving; startup retains this routing owner across store open, serve and shutdown (`runtime/startup.cpp:237-280,430-444`). The gateway entry awaits `startup::run`; offline entrypoints have no capturing coroutine. Existing server drain/shutdown acceptance remains separate from this static ownership conclusion.
