# Rust Worker real-provider e2e on the VPS (2026-11-05)

This is a go/no-go input for promotion of the Rust gateway Worker. It follows `rust-worker-local-e2e-2026-11-05.md`, which used only synthetic or denied upstreams. This run executed one test build of the Worker under the pinned Miniflare/workerd on the production VPS host. Outbound requests were not intercepted, so the Worker called the real DeepSeek, Cerebras and OpenRouter APIs with the production provider keys.

Owner authorization (2026-11-05): inference tests against cheap models with low reasoning. Each case sent one small request. No secret value was printed, logged, written to a file or committed. No Codex or OAuth credential was bound, read or refreshed. The production gateway, its `.env`, KV, service and checkout were not modified; the `.env` was only sourced, read-only, inside the test subshell. Nothing was deployed.

## Runtime configuration

The Miniflare options were the same as in the local run: the explicit three-module list (`entrypoint.mjs`, `build/index.js`, CompiledWasm `build/index_bg.wasm`), `compatibilityDate 2026-10-18`, `enable_request_signal` and `request_signal_passthrough`, the SQLite Durable Object `AUTHORITY` → `GatewayAuthority`, and `ASSETS` from `static/` with the Worker running first. There were two differences: no `outboundService` was configured, and the bindings were different.

Bindings:

- `DEEPSEEK_API_KEY`, `CEREBRAS_API_KEY`, `OPENROUTER_API_KEY` were taken from the production `.env`. Only the three names were passed, through `set -a; . .env; set +a; exec env -i PATH=… HOME=… DEEPSEEK_API_KEY=… CEREBRAS_API_KEY=… OPENROUTER_API_KEY=… node run-vps*.mjs`. The values went only into the Miniflare process environment and its bindings.
- `UOS_AI_TOKEN` and `DENO_DEPLOY_TOKEN` (the Worker's admin-token source) were set to fresh random values generated per run. The production `DENO_DEPLOY_TOKEN` was not used.
- These were left unset on purpose: `LITHOSAI_API_KEY`, `SURPLUS_API_KEY`, `METERED_API_KEY`, `CLAUDE_API_KEY`, every Codex binding (`CODEX_AUTH_JSON_B64` and the rest), Passport bindings, and native-owner bindings. With them unset, the Codex, Claude Code, Lithos and OpenLux paths stay unconfigured and the paid waterfall cannot be reached.
- Provider selection was set through `POST /admin/providers/selection {"provider_ids":["deepseek","cerebras","openrouter"]}` (200 `stored:true`). Codex was never enabled.
- Inference used an API key created through `POST /admin/api-keys` (defaults: 50 requests per 7-day window, `paid_fallback_enabled:false`), so that per-key ledger rows could be inspected.

The harness redacted every provider key, both random tokens and the created `u_…` key from the transcripts before writing them. The transcripts are scratch evidence and are not committed.

## Findings for promotion review

1. **Real-provider wire compatibility works for DeepSeek and OpenRouter.** DeepSeek served Chat Completions (non-stream and incremental stream) and Responses (non-stream and stream, translated from Chat Completions, with reasoning summaries). OpenRouter served a Responses stream. Status codes, `x-uos-upstream`, release identity headers and usage all came back correctly from the real APIs.
2. **The Cerebras production key is being refused with 402 `payment_required`.** This is a provider-account billing state, not a Worker fault. The Worker returned the upstream envelope as JSON without starting SSE and recorded `http_402`. It means the AGENTS.md Cerebras `gpt-oss-120b` buffered-replay behaviour was not exercised against the real provider. The production Bun gateway, which uses the same key, presumably gets the same 402; that was not checked, to avoid touching production.
3. **Chat Completions requests record no token usage in the Worker's ledger or observability rollup.** DeepSeek returned usage in every Chat Completions body or stream, but every `chat.completions` ledger row has `input_tokens:null, output_tokens:null`. The quota projection counted only the two Responses requests (`request_count:2`, 74/23 tokens). Responses rows (DeepSeek and OpenRouter) do record tokens. Billing is `not_applicable` for direct providers, so no spend is mis-settled here. However, per-model usage observability under-reports Chat Completions traffic. Compare this with the TypeScript gateway before promotion.
4. **Unexplained pre-dispatch latency of about 2.5 to 3.3 s on inference.** The client time to first byte on inference was 3.1 to 4.1 s. The Worker's own `latency_ms` for the same requests was 0.66 to 1.1 s. Health took 4 to 102 ms, and admin reads 20 to 108 ms. Two concurrent requests took about 6.5 s each, while their ledger latencies were about 1 s, which suggests the pre-dispatch work is serialized. Warm `/v1/models` reads also took 3.5 to 4.9 s. The likely but **unverified** cause is live provider catalog discovery (OpenRouter has about 800 models) on every inference request or catalog read. Confirming it needs outbound observation, which this run deliberately did not install. Investigate this before promotion; Cloudflare caching may behave differently.
5. **Non-OpenAI fields pass through from providers.** Seen: DeepSeek `reasoning_content`, `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` and `system_fingerprint` in Chat Completions; OpenRouter `cost`, `is_byok` and `cost_details` inside Responses `usage`. In addition, Responses bodies echo `max_output_tokens:null` and `reasoning:null` even when the request set them. These need a check against the OpenAI-schema rule in AGENTS.md and against the TypeScript gateway's behaviour. They were only observed here.
6. With `max_completion_tokens:32` and `reasoning_effort:"low"`, the DeepSeek stream spent 30 tokens reasoning and ended with `finish_reason:"length"`. The non-stream request spent 0. Low budgets with DeepSeek thinking are therefore non-deterministic, and the gateway classifies a length stop as `response.incomplete`.
7. `provider_request_id` is null on every ledger row, and no `x-uos-provider-request-id` header was returned, although DeepSeek and OpenRouter return response ids. Correlating a request with the provider is therefore not possible from the Worker's records.

## Abort observability (row 9)

What was observed: the Worker streamed incrementally. The client cancelled after 4 frames at 4,385 ms. The Worker closed its ledger row with `latency_ms` 941. Measured from the dispatch point (client TTFB minus about 3.1 s of pre-dispatch work), that is close to the abort time, not to the time needed to generate 120 numbers. The Worker therefore observed the client disconnect promptly and finalized the row. It stayed healthy, answering `/health` in 5 ms.

What could not be observed:

- Whether the upstream DeepSeek HTTP request was actually cancelled. DeepSeek returned no usage frame to the client before the abort. The Worker's ledger stores no tokens for chat rows (finding 3), and DeepSeek offers no per-request usage lookup. The account billing dashboard was not accessed. The upstream could have generated the remaining approximately 200 tokens and billed them, and this run cannot distinguish that from a clean cancel.
- The ledger and `/admin/errors` do not mark the request as client-aborted. It looks like an ordinary 200, so delivery outcome on abort is not recorded where an operator would look.

Upstream cancellation remains unproven, as it was in the local run's row 21b. It needs an observable upstream on the real Cloudflare runtime, or provider-side usage reconciliation.

## Spend estimate

- DeepSeek: 8 requests with about 210 input tokens in total and about 60 output tokens observed, plus at most about 200 unobserved output tokens from the aborted stream. Even at a deliberately high bound of $1 per million input tokens and $2 per million output tokens, that is under $0.001.
- OpenRouter: the provider reported `cost 4.158e-7` (about $0.0000004).
- Cerebras: 402 rejections, presumably not billed.
- Catalog discovery (OpenRouter and Surplus model lists): free endpoints.

**Total: under $0.001.**

## Still unproven

- **Cloudflare runtime**: isolates, Durable Object placement and real storage, `request_signal_passthrough` semantics, CPU, memory and upload-size limits, the assets router, caching of catalog discovery, routes and DNS. Everything here ran under local workerd on the VPS.
- **Codex subscription path**: no Codex credential was bound (by rule). The global active subscription, the waterfall to Surplus and OpenLux, authoritative exhaustion handling, banked resets and the Codex-native `/v1/models?client_version=` catalog were not exercised against real upstreams.
- **Paid waterfall and settlement**: Surplus and OpenLux were not bound. Exactly-once paid settlement, reservations and `spend_microcredits` were not exercised. Every row here is `not_applicable`.
- **Cerebras success path**: the provider account returns 402. The buffered non-streaming replay for `gpt-oss-120b`, and the `cerebras_upstream_invalid_response` length case, are unobserved against the real API.
- **Lithos, Claude/Anthropic and the `ubiquity/deepseek-flash` synthetic waterfall**: not exercised.
- **Upstream cancellation on client disconnect**: see "Abort observability" above.
- **Native owner**: the `UOS_NATIVE_CARRIER` and supervisor sidebands, and `InitialControlInstaller`.
- **Data migration**: the KV-to-Durable-Object import and validation (`/admin/kv-migration/*`) against production data. Every run started from an empty Durable Object.
- **The ARM64 exact-source build** (`ops/rust-worker-build.sh`), CI gates, and a deployed authenticated inference receipt with `/health` identity.
