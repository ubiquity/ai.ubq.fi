# Assistant turn unit economics

Date calculated: 2026-07-21 Long-context update: 2026-07-26

## Recommendation

Charge **at least one application credit per user-initiated Assistant turn**, then settle additional credits from the
total model usage generated by that turn. A single user action may invoke the model up to eight times, so charging a
fixed one credit for every possible turn would expose the product to losses on bulk-attachment Agent loops.

A practical initial schedule is:

| Turn class                         | Suggested application credits |
| ---------------------------------- | ----------------------------: |
| Brief or ordinary answer           |                             1 |
| Ordinary multi-call Agent turn     |                             2 |
| Heavy contextual Agent turn        |                           3-8 |
| Maximum bulk-attachment Agent turn |                Up to about 20 |
| Measured single-call 600K context  |                           264 |

The application can present this as one credit for ordinary chat and “additional credits for deep Agent work,” rather
than exposing raw tokens to customers.

## One-million-token-window economics

Enabling Terra's large API context window has no fixed charge; billing depends on the tokens actually processed. OpenAI
documents a 1,050,000-token API context window for GPT-5.6 Terra, with a maximum of 922,000 input tokens and 128,000
output tokens. Once API input exceeds 272,000 tokens, the entire request is billed at twice the normal input rate and
1.5 times the normal output rate.

That makes official OpenAI API long-context pricing:

| Token type   | OpenAI retail per million |
| ------------ | ------------------------: |
| Input        |                     $5.00 |
| Cached input |                     $0.50 |
| Output       |                    $22.50 |

The earlier catalog-only estimate assumed metered would retain the cheap `Codex专属` group above 272K. A live test on
2026-07-26 disproved that assumption.

### Measured 600K long-context test

A synthetic prompt contained unique markers at approximately 300K, 500K, and 580K tokens. metered returned every marker
exactly:

```text
M300K_18F4A7C2|M500K_6D91E3B8|M580K_A52C79D4
```

The Responses result and billing console reported:

| Measure         | Result                                        |
| --------------- | --------------------------------------------- |
| Model           | `gpt-5.6-terra`                               |
| Input           | 600,086 tokens                                |
| Cached input    | 0 tokens                                      |
| Output          | 65 tokens, including 26 reasoning tokens      |
| End-to-end time | 326.2 seconds; console rounded to 324 seconds |
| Retrieval       | All three markers recovered                   |
| metered group     | `官转`, not the cheap `Codex专属` group       |
| Model ratio     | 1.25                                          |
| Group ratio     | 3                                             |
| Tier multiplier | Input 2; output 1.5                           |
| Deduction       | 9.005678 metered credits                        |

The console displayed this exact billing formula:

```text
(600086 / 1M × 2.5 × 2 + 65 / 1M × 15 × 1.5) × 3
= 9.005678 metered credits
```

At 0.495 CNY per metered credit and 6.7722 CNY/USD, this cost approximately $0.6583. The same uncached usage at OpenAI
retail is approximately $3.0019. Metered's measured long-context route therefore cost **21.93% of OpenAI retail**, or
**4.56x less**, rather than the 85.5x discount observed or projected for the subscription-backed short-context route.

The measured effective long-context rates are:

| Token type | OpenAI retail | metered `官转` | OpenAI/Metered |
| ---------- | ------------: | -----------: | -----------: |
| Input      |       $5.00/M |    $1.0964/M |        4.56x |
| Output     |      $22.50/M |    $4.9338/M |        4.56x |

### Flex-processing hypothesis

OpenAI publicly prices Flex processing at the same rates as Batch while retaining a synchronous Responses or Chat
Completions interface. For long-context Terra, the published Flex prices are $2.50/M input and $11.25/M output, exactly
half the standard rates. OpenAI describes Flex as lower cost in exchange for slower responses and occasional resource
unavailability, and recommends allowing timeouts up to 15 minutes for lengthy prompts.

For the measured request:

| Route                 | Equivalent cost | Relative to metered |
| --------------------- | --------------: | ----------------: |
| OpenAI standard       |         $3.0019 |             4.56x |
| OpenAI public Flex    |         $1.5009 |             2.28x |
| metered measured `官转` |         $0.6583 |             1.00x |

The 326-second response time is consistent with Flex-like processing. If metered injected `service_tier: "flex"` upstream,
public Flex pricing explains the first 50% discount. metered would then still be charging only 43.86% of public Flex
pricing, requiring another 56.14% reduction or subsidy.

This remains an inference: the original metered result was not saved with its full `service_tier` field, metered does not
support retrieving the completed response by ID, and the billing console does not display the upstream service tier.

### Grey-market profitability model

The measured $0.6583 receipt is too low to profit from public Flex alone, but a reseller does not need every upstream
request to have the same acquisition cost. Let `f` be the share of equivalent traffic purchased at public Flex and
assume the remainder is supplied at approximately zero marginal cash cost through promotional credits, compromised
credentials or billing accounts, refunds or chargebacks, or a third party paying for the resulting data:

```text
average upstream cost = f × $1.5009
```

The resulting limits are:

| Target before infrastructure and payment costs | Maximum public-Flex share | Required near-zero-cost share |
| ---------------------------------------------- | ------------------------: | ----------------------------: |
| Break even                                     |                    43.86% |                        56.14% |
| 20% gross margin                               |                    35.09% |                        64.91% |
| 30% gross margin                               |                    30.70% |                        69.30% |

This makes a blended grey-market pool economically coherent without requiring OpenAI to grant one customer a 78%
discount. Reported mechanisms in the broader Chinese relay market include farming free or promotional credits,
subdividing fixed-price subscriptions where applicable, stolen credentials or payment cards, corporate discounts, model
substitution, and treating collected prompts and outputs as the economically valuable product. Those reports are
evidence about the market, not proof of Metered's specific supply chain.

For Metered's verified long-context route, subscription subdivision cannot explain inputs above 272K. The remaining
credible sources are API-class Flex or contracted capacity combined with discounted, promotional, fraudulently funded,
or data-subsidized supply.

For a 600K-input plus 65-output turn, the provider cost alone consumes about 53 application credits at the $0.0125
Scale-pack value. Preserving an 80% gross margin would require about 264 application credits.

### Practical window limitation

An initial locally tokenized 870,078-token test was rejected before inference with HTTP 413:

```text
Input token count (1252901) exceeds system limit (1000000)
```

The successful 600K test proves genuine processing well beyond the Codex subscription model's 272K window, but the
rejection means metered does not expose OpenAI's documented 1.05M/922K API envelope verbatim. The maximum usable payload
needs further calibration and may depend on Metered's preprocessing or reserved context.

The synthetic filler was `" x"` repeated. It encodes as exactly one token under both `o200k_base` and `cl100k_base`.
Local `o200k_base` tokenization counted 600,080 tokens for the successful request; Metered's completed response reported
600,086, a difference of only six wrapper tokens (0.001%). Therefore the successful request's positions and billing
count are empirically validated and do not depend on guessing the model tokenizer. The rejected 870K request's
1,252,901-token preflight count is inconsistent with this near-exact match and points instead to a different or faulty
limit estimator, reserved-context calculation, or gateway preprocessing path.

### Documentation boundary: API versus Codex subscription

OpenAI's published Codex plan table includes Terra for Plus, Pro 5x, Pro 20x, and Business users. It says that extended
sessions holding more context consume more allowance per message, but it does **not** state that ChatGPT-authenticated
Codex exposes Terra's full 1.05M API window.

The authenticated Codex CLI model catalog cached on the test machine advertised `gpt-5.6-terra` with a 272,000-token
context window and a 95% effective window. This is direct runtime evidence against assuming that pooled ordinary Codex
subscriptions can supply inputs above 272K.

The live test shows that metered switches long-context traffic to the separate `官转` group and applies substantially
higher pricing. That group can process at least 600K input tokens. Its exact upstream supply remains unverified;
plausible explanations include:

- an official API, Enterprise, Azure, or other contracted upstream;
- promotional or fraudulently funded API accounts;
- loss-leading pricing or revenue from retained request data;
- a separate long-context group with different supply economics; or
- a route that truncates, rejects, or does not fully process the advertised context.

The observed 4.56x discount is much more compatible with an API-class discounted or subsidized upstream than the
previous hypothetical 85.5x figure. The test proves usable 600K context and separate routing, but cannot distinguish an
Enterprise discount from other funding or supply mechanisms.

| ------- | ----: | ----------------------------: | -------------------------: |

Assistant margin.

The following estimates conservatively treat all input as uncached. Completion counts include visible output and any
reasoning tokens included in Metered's billed completion usage.

| Turn shape                   | Cumulative input | Cumulative completion | metered cost | Cost in cents |
| ---------------------------- | ---------------: | --------------------: | ---------: | ------------: |
| Brief, one call              |            5,000 |                   750 |  $0.000278 |        0.028c |
| Ordinary, one call           |           27,000 |                 1,500 |  $0.001052 |        0.105c |
| Ordinary Agent, three calls  |           81,000 |                 4,500 |  $0.003156 |        0.316c |
| Heavy Agent, three calls     |          204,000 |                 6,000 |  $0.007012 |        0.701c |

table intentionally does not rely on cache hits when setting retail prices.

## Usage-based settlement formula for calls at or below 272K

Terra completion tokens cost six times as much as uncached input, while cached input costs one tenth as much. Define
uncached-input-equivalent tokens for every model call belonging to one user action:

```text
equivalent tokens = uncached input + 0.1 x cached input + 6 x completion
```

At the live `0.8x` metered rate:

```text
provider cost ≈ equivalent tokens / 1,000,000 x $0.02922
```

For an approximately 80% gross margin against the cheapest application-credit pack, allow at most $0.0025 of provider
cost per application credit. This produces a simple settlement rule:

```text
application credits charged = max(1, ceil(equivalent tokens / 85,000))
```

Applied to the conservative scenarios above, this charges 1, 1, 2, 3, 8, and 21 credits respectively. A softer target
near 70% gross margin would use approximately 128,000 equivalent tokens per credit instead.

Do not apply this formula to a single call above 272K. The measured long-context route uses different group economics:

```text
provider cost in USD =
  (
    input / 1M × 2.5 × 2
    + output / 1M × 15 × 1.5
  )
  × group ratio 3
  × $0.07309 per metered credit

application credits at 80% gross margin =
  ceil(provider cost in USD / $0.0025)
```

## Product and accounting requirements

The charge should be computed across the entire user-initiated action, not separately displayed for invisible model
continuations. Before starting, reserve a bounded maximum; after completion, settle actual usage and release the rest.

Record at minimum:

- uncached input tokens;
- cached input tokens;
- completion and reasoning tokens;
- model-call count;
- attachment count and serialized attachment bytes;
- the provider route and group multiplier; and
- the pricing-version identifier used for settlement.

Until those measurements exist, use one credit for ordinary chat, meter multi-call turns with the formula above, and cap
attached-record Agent work rather than promising every user action for one fixed credit.
